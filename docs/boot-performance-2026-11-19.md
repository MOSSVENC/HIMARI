# 启动性能调查与验证

目标设备：Firebat/Clevo ZY-T6K，Ryzen 7 7745HX。

## 当前结论

开机进入桌面后的低性能根因尚未确认，不能将设置回读成功当作
CPU 恢复性能的证据。现有控制中心也尚未完成全部原厂功能验收；
分项状态见 [功能覆盖](cc40-feature-parity.md#acceptance-status--2026-11-19)。

本次已确认并修正的协议差异是：性能模式的硬件命令需要保留
Turbo 风扇标志；Quiet+ 的持久化值与硬件命令值不同。原厂命令 79
的解码名称是 SetEnergyStarMode，先前称其为 CPU boost 并据此推断
开机性能恢复，缺乏证据。该命令仍按本机已恢复的原厂映射执行。

## 启动现场证据

2026-11-18（本机时间 UTC+8）的一次启动：

| 事件 | 时间 |
|---|---|
| Windows 启动时间 | 21:22:07.500 |
| DCHUService 进程创建 | 21:22:43.881 |
| RAM 启动服务开始策略回放 | 21:22:44.888 |
| 模式写入及回读完成 | 21:22:44.993 |
| Explorer 进程创建 | 21:23:05.013 |
| FnKey 进程创建 | 21:23:20.623 |
| 原厂记录 ChangePowerMode(GetPowerMode()) | 21:23:22.604 |

这次 RAM 策略回放早于 Explorer 约 20 秒，因此不能解释为“服务在
桌面之后才启动”。这份日志没有记录当时的实时 CPU 频率或负载。
原厂随后仍会执行自己的模式回放；目前也没有证据证明它覆盖了错误状态。

本次只读检查中，当前 CPU 频率采样可变化，Windows 电源计划处于
自定义卓越性能方案；这些是桌面运行后的状态，不能反推冷启动表现。
启动区间的 Kernel-Processor-Power 事件返回 CPPC 能力信息，未返回
固件限频事件；事件缺失同样不能排除实际低性能。

## 原厂流程对照

分析对象为本机 FnKey.exe，哈希见 [Fn 事件协议](fn-event-protocol.md)。
原始二进制、反编译输出和完整设备日志保存在本机忽略目录中。

- 模式设置写入 AppSettings，然后发送 121/25 和 Energy Star 命令。
- 性能模式会将已启用的 Turbo 风扇标志并入 121/25 的硬件值。
- Quiet+ 保存 UI 值 4，但硬件命令值为 0。
- Release PROC_HOT 位于带机型和平台条件的额外 CPU 调整流程。
  已观察到的本机 SSID 为 0x28a1，与主要初始化分支中的
  0x50f0/0x50f4 不匹配；本机启动日志也未观察到该调用。
  其他调用条件仍需核对，当前未将该命令加入控制实现。

## 现有服务中的 CPU 观察

策略回放成功后，同一进程默认观察 60 秒，再退出。首次电源写入在
创建 CPU 采样器之前执行。服务已报告 Running，观察过程不阻塞
Windows 启动其他服务或打开应用界面。

记录写入应用现有 boot-agent.log，包括：

- CPU 采样时的系统运行时长、实际性能计数器换算频率、标称频率和负载；
- 当前模式与策略镜像，以及 Windows 活动电源方案；
- 独立间隔采样的 CPU 温度及样本年龄；
- 有效样本数量与观察到的频率范围。

计数器缺失显示为 None，不伪装成 0 MHz 或空闲。CPU 观察本身只有
读取操作，温度失效保留为未知。CPU 采样器与概览共用同一实现，
该启动路径不初始化 GPU 遥测或界面。

手动诊断使用现有 EXE：

```powershell
& 'C:\ProgramData\Himari\himari.exe' --boot-agent --observe-only --observe-ms 5000
```

`--observe-only` 跳过模式、风扇写入和驱动服务启动；`--observe-ms`
限制为 0–60000。正式启动服务中的观察在现有策略回放之后执行。
部署脚本为设备就绪重试、回放及观察保留 195 秒等待窗口。

下一次经过用户安排的冷启动仍是必要验证：对齐这份记录、原厂事件
和桌面卡顿区间，才能区分真实低频、策略漂移和其他响应阻塞。
