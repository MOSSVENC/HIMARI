# 输入配对与 FlexiKey 响应验证

## 已复现的缺陷

删除或切换绑定时，旧实现清空按下记录。最初被吞掉的按下，其后续重复事件可能传给 Windows，释放却再次被吞掉。录制触发键时也存在重复按下与释放不配对的路径。回归用例在原实现上失败，记录位于本机 target/validation/input-routing/baseline-regression.log。

原 FlexiKey 界面回调直接更新钩子并保存 XML。钩子命令确认最多等待 3 秒，文件系统操作也在界面线程执行；切换配置成功后还会再次更新输入引擎。

## 当前实现

- input_bindings.rs 统一管理键盘、鼠标和录制状态。一次物理按下确定该组重复、释放事件的归属；更换绑定、取消或重新录制保留该归属。必要的钩子持续到待配对释放处理完毕。
- 新启用钩子在处理消息前登记已经按住的物理键，避免接管其后续重复和释放。
- input_hooks.rs 先准备新增句柄，再修改已有句柄。新增设备失败保留原有钩子；命令传输失败或超时才进入线程停止路径。
- flexikey_jobs.rs 使用一个常驻配置线程和容量 32 的队列，串行执行运行时配置、写盘和回滚。输入回调使用非阻塞通知；界面回调提交完整草稿后立即返回。
- 结果携带请求编号。旧请求的完成结果不会覆盖较新的界面草稿；最新请求失败时恢复工作线程保存的最后一次成功状态。写盘失败和运行时恢复失败分别报告。
- 录制请求有独立代次。关闭编辑器、取消或重新开始录制，会使排队中的旧请求失效；配置过程中发生取消，也会在完成后撤销旧录制。
- flexikey_store.rs 集中处理 XML 与文件替换。界面文件负责草稿、校验和展示。

## 宏回放的释放与扩展键

进一步检查发现，原回放循环在某个步骤发送失败时立即返回，没有释放先前已经成功按下的键。文本的 Unicode 按下和释放原先一次提交，部分成功也没有清理路径。扩展扫描码在转换虚拟键前丢失 E0/E1 前缀，可能把 Delete、方向键、右 Ctrl、数字键盘除号和 Pause 转换成其他键。

input_replay.rs 负责单次按键或文本动作的校验、按键归属与释放；Windows 适配层保留实际输入发送和扫描码转换。完整动作先通过键码校验，再执行延迟和输入。每次成功按下后记录归属，正常结束或发送失败均按相反顺序尝试释放剩余按键；个别释放失败不会中止其他键的清理，错误分别保留。检测到原先已经按住的键时，宏保留用户对它的控制；孤立的释放事件不发送。文本动作的起始快捷键、正文和末尾快捷键共用同一份归属记录，支持跨正文保持修饰键。

扩展扫描码使用完整值调用 MapVirtualKeyW；E0 与 Pause 的 E1 前缀分别处理。Unicode 逐事件发送并登记成功结果。Windows 拒绝释放、进程被强制终止或物理输入在发送间隙变化仍属于需要单独观察的边界，软件清理不能保证这些条件下的系统键状态。

故障注入使用内存中的 ReplaySink，逐一拒绝和弦及中英文、代理对文本动作的每个事件，检查已经成功发送的按下最终配对释放。另覆盖已有物理按键、孤立释放、重复按下、缺少末尾释放、非法末尾键码、清理失败后继续释放其他键和延迟边界。Windows 原生测试直接检查扩展键的虚拟键编码与标志；这些检查不向桌面发送键鼠事件。

本轮不能证明原厂 FnKey、HKClipSvc、键鼠过滤驱动与本应用共存时的物理输入故障已经根除，实机共存验收继续保留。

## 启动阶段键鼠过滤冲突

已安装的 `HKKbdFltr` 和 `HKMouFltr` 位于键盘、鼠标类的 `UpperFilters` 首位。原厂键盘过滤器的 `0xBA400` 控制拦截是否启用，`0xBA41C` 控制 USB 键盘是否进入该过滤链。实机扫描同时确认：鼠标过滤器接口不接受这两个键盘控制码，返回 `ERROR_INVALID_FUNCTION`。

原厂 `CC40/kb.dll` 静态导入 `HKFltrLib`，并调用 `HKFltrLib_OpenDevice`、`HKFltrLib_EnableFilter` 和宏注册接口。过滤器设备及其开关是机器级共享状态，不携带客户端所有权；HIMARI 又会在原实现里通过打开设备探测驱动健康。两套客户端同时运行时，最后写入者决定共享状态，启动先后和设备枚举快慢会改变结果，因此共存时故障呈时序性、偶发性，而非每次稳定复现。

HIMARI 的 FlexiKey 使用自有的低级键盘/鼠标钩子，不需要原厂过滤器的宏拦截。当前行为是：

- 驱动健康检查读取服务状态，不再周期性打开过滤器设备；
- 检测到原厂 `CC40.exe`、`ControlCenter30.exe`、`COUWP.exe` 或 `ControlCenter.exe` 运行时，本程序让出输入过滤所有权，不与其争写；
- 原厂控制中心退出后，本程序恢复自己的过滤器旁路；
- 启动服务在请求 AcpiBridge 和执行电源回放之前调用守护，桌面进程启动后也会启动同一守护。

守护每五秒重新确认以下状态：

```text
HKKbdFltr 0xBA41C(false)  USB keyboard bypass
HKKbdFltr 0xBA400(false)  interception disabled
```

守护只发送运行期控制码，不卸载驱动、不改注册表、不改固件，也不删除原厂服务。正常启动时的守护回执固定写入 `C:\ProgramData\Himari\input-guard.log`，开发期控制码扫描记录在本机忽略目录 `target/validation/input-incident/filter-reenable.txt`。

这一定位解释了故障的场景边界：外接 USB 键鼠在启动后失效，而碰触内置键盘可使输入链重新同步；它不把当前桌面状态或一次成功控制码调用当作冷启动验收。下一次重启后仍需检查外接键鼠在 Explorer 出现后的连续输入，以及 Ctrl/Win 的组合键状态。

```text

```
