# Fn 事件协议与验证

分析日期：2026-11-17。分析对象是本机 FnKey.exe，SHA-256：

```text
bfb43dee6c5fbcf4315bd1a90ebaa2f997715a2677230523a195f3aac5afd4d6
```

原始二进制、IL、字符串解码输出保存在本机忽略目录 `docs/research/fn-events/` 和 `target/validation/`。本文件记录独立实现所需的帧格式和行为证据。

## 传输与分发

设备为 AcpiBridge `CLV0001`。FnKey 中 RVA `0x3446c` 的后台方法先发送一次 `0x322404` 注册事件句柄，然后循环等待事件、读取 `0x322408` 的 8 字节有符号整数，并将结果写为 `Arg001^<十进制值>`。这个循环本身只负责投递。

FnKey 的 EventLog 接收回调 RVA `0x125f0` 在 IL `05d0–0621` 区段识别 `Arg001`，将数值转换成 i32，再分为：

```text
事件编号 = value & 255
参数     = value >> 8（有符号右移）
```

RVA `0xdd10` 将这两个参数调度到 UI 线程；嵌套回调 RVA `0x133b0` 执行具体分支。OSD 枚举是另一套资源索引，例如资源 24 为触摸板关闭图片，而硬件事件 24 没有这个含义。

`fn_events.rs` 保留完整 i64 原值，只对 i32 可表示的通知提取编号和参数；短帧、长帧返回错误。超出该格式的通知保留原值，等待进一步分析。

`fc/fd` 的精确触摸板分支都会先读取 Windows 注册表的当前启用状态，再选择相反状态。因此直接把 `fc` 映射成固定关闭、`fd` 映射成固定开启，会偏离本机原厂行为。解析模型保留旧设备目标值，供后续按能力选择执行路径。

电源、摄像头、触摸板、Fn 锁定等分支包含状态变化；Caps Lock 等分支主要展示状态。风扇提示同样可能伴随原厂附加操作。解析模型不把提示编号直接当作应再次写入硬件的控制命令。

## 实现与验收范围

- 通知订阅在 `open()` 中注册一次；只有注册成功才报告已就绪。设备句柄先于其引用的事件句柄释放。
- `wait_next_timeout()` 支持重复限时等待；超时保留订阅，下次继续等待。仅事件被触发时才读取通知载荷。
- `--trace-fn-events` 记录原始值、编号 / 参数和已识别事件。
- `--fn-events-smoke` 注册一次并执行三次 150 ms 等待后释放句柄。应在协调 FnKey 通道所有权后运行。
- 单元测试覆盖帧长度、参数分离、有符号右移、整数溢出别名、触摸板语义和资源编号隔离。

常驻 Fn owner 已接入交互进程，但在 `FnKey.exe` 运行时会主动让出；只有原厂 FnKey 和转发服务退出、AppSettings 1/12 为 0 时才注册直接订阅。已映射事件会执行电源、键盘背光、Fn Lock、风扇、摄像头、触摸板和控制中心开关等动作，并通过独立 Slint OSD 显示结果。

`--osd-smoke` 验证底部居中 OSD 的窗口和自动隐藏；`--fn-event-smoke <code>` 用合成通知验证生产分发路径。本机各个 Fn 组合实际产生的通知、接管瞬间的物理按键、多客户端投递行为以及每个硬件分支仍需逐项实机验收。

## 本机订阅生命周期验证

2026-11-17，在确认唯一的 FnKey 进程及其完整恢复路径后，暂时停止该进程，连续执行两次 Release `--fn-events-smoke`，最后重新启动并核对原路径。测试期间 FnKey 未自行重启。

两次均成功注册、执行三次等待并关闭订阅；六次等待均为超时，实际用时 155–162 ms。第二次注册成功说明本次关闭后能够重新订阅。记录位于本机 `target/validation/windows-fn-subscription.log`。

这次测试期间 CCDCHUService 仍在运行，因此仅证明调用成功和句柄生命周期；它没有隔离全部厂商监听方，也没有捕获物理按键通知。Windows 原生单元测试共 73 项通过，其中六项新增测试覆盖本模块的帧与解析规则。

## 服务转发归属与完整隔离测试

进一步分析本机 `DCHUService.exe`，SHA-256 为 `7a8f670e35b72d9b270ca4abdb3d330c0451029ab107791006fc847a22eb2fc6`：

- `DCHU.DoEventWork` RVA `0x5cd8` 在注册事件前调用 `SetArg001_bySendStatus(1)`，读取通知后写入 `Arg001^<值>`；退出清理调用该方法并传入 0。
- `SetArg001_bySendStatus` RVA `0x5e3c` 向 AppSettings page 1 / offset 12 写一个字节，值为参数的低字节。
- `Service1.OnStop` RVA `0x67cc` 同样将该标记写为 0。
- FnKey RVA `0x25a00` 读取该字段。值为 1 时记录 `Arg001Event by DCHUService Send`；其他值创建直接监听对象，并记录 `Arg001Event by FnKey Send`。

因此该字节表示服务转发归属。应用的两项显式诊断在订阅前查询 `CCDCHUService` / `DCHUService`，并要求该字节为 0；查询失败、未知值或活动服务均返回错误。调用方仍需协调 FnKey，运行期间服务重启和多客户端投递尚待验证。

`scripts/test-fn-events.ps1` 保存原有服务状态和 FnKey 路径，验证占用时拒绝注册，再暂停原厂服务与 FnKey，执行两次订阅测试，最后恢复两者。2026-11-17 本机结果：

- 服务运行时读取标记 1，诊断返回所有权错误，尚未注册。
- 服务停止后确认进程退出，读取标记 0；连续两次注册、三次等待、释放均成功。六次等待均超时，实际 150–157 ms。
- 原服务恢复为 Running，FnKey 恢复到原路径。完整记录为本机 `target/validation/windows-fn-owner.log`。
- Windows 原生 75 项测试通过；新增两项覆盖服务转发、未知和不可读标记拒绝路径。

该测试没有发送物理按键，仍不能作为热键投递、动作或 OSD 完成的证据。

## 常驻接管实测

2026-11-19 进行了可逆所有权切换：停止原厂 `FnKey.exe` 与
`CCDCHUService`，启动 RAM CONTROL CENTER，常驻 owner 成功输出
`Fn notification channel acquired`。随后停止测试进程，恢复服务和 FnKey，
再启动 RAM CONTROL CENTER；恢复结果为服务 Running、FnKey 进程存在、后台单实例。
该测试证明通知通道可由独立实现获取和释放，但不等于已经完成物理 Fn 组合逐项验收。

2026-11-19 的物理接管日志还发现驱动可能返回 4 字节通知。协议层现在同时接受
4 字节有符号 i32 与 8 字节 i64，i32 会符号扩展到 i64；第二次接管只验证了通道获取，
没有捕获新的物理按键通知，因此不能把该轮视为 Fn 动作验收。
